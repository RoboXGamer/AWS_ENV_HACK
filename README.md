# PackIQ — Smart Packaging Optimization Platform

## The problem

E-commerce sellers and warehouses routinely ship small products in oversized boxes, filling the leftover space with bubble wrap, void fill and extra cardboard. This is usually done by hand or with a rule of thumb like "always use the medium box", so nobody can see the true cost. The damage compounds on every shipment: more cartons bought than necessary, more dimensional-weight charged by the courier, and more material sent to landfill. The core difficulty is that the right answer is not obvious by eye — it depends on how product dimensions, rotations, box sizes and weight limits interact across an entire order, which is exactly the kind of combinatorial question people cannot solve reliably by intuition.

## The solution we implemented

PackIQ takes a list of products (length, width, height, weight, quantity) and the box sizes actually available to you, then produces a concrete packing plan that fits the maximum number of items into the minimum sensible material and shipping volume. The engine expands every product unit, sorts them with one of several deterministic orderings, and places each item using maximal-space anchor points: it scans candidate positions against all six axis rotations and keeps whichever placement has the largest contact area against items already packed, which is what makes the result dense and surface-conforming. It then greedily selects the cheapest effective box at each step, where effective cost combines cardboard cost with volumetric shipping so that large boxes are not chosen just because they are cheap per square metre. Several orderings are tried and the best plan is kept, after which the dashboard shows exactly how everything fits in an interactive 3D view, alongside space utilization, boxes required, cardboard and shipping cost saved, and a direct comparison against the naive one-item-per-box approach. The whole search is deterministic: there is no randomness and no time-dependent decision anywhere, so the same inputs always produce an identical plan, which makes results reproducible, testable and safe to trust in an operational context. The engine is written as pure TypeScript with no DOM or React dependencies, so the exact same code runs inside a Web Worker in the browser and under the test suite.

## Current tech stack

The front end is React 18 with TypeScript, built and served by Vite 5. The 3D visualization is built on Three.js with OrbitControls, mapping the packer's coordinate space (x = length, y = width, z = height) onto three's Y-up axes. All optimization runs in a Web Worker so a multi-second packing search never blocks the UI, and the engine module itself is framework-free, which is what allows it to be reused unchanged in a serverless function later. Data entry is manual via editable tables plus CSV import and export, and the working dataset persists to `localStorage`. Tests are written with Vitest and cover placement validity (no overlaps, in-bounds, weight limits), determinism, box selection, CSV round-tripping, and the 3D coordinate mapping. There is currently no backend and no AWS involvement: the app is fully static and intended to be deployed to S3 plus CloudFront, which sits inside AWS's always-free allowances at zero monthly cost, while heavier future needs (database, auth, AI) are deliberately left to other providers' free tiers.
